# Updates: November 24, 2026

The first weekly import from Wikidata brought in far more finds than expected. This update narrows
the import to the Holy Land and keeps unchecked finds off the map unless a visitor asks for them.

## Fewer, closer finds from Wikidata

### What changed

The Weekly data workflow ran for the first time on November 23. It imported 1,192 finds from
Wikidata, most of them museum objects from places far from the Holy Land:

| Place | Finds |
|---|---|
| Heliopolis, Egypt | 419 |
| Susa, Iran | 157 |
| Rome | 89 |
| Thebes, Egypt | 72 |
| Cyprus | 70 |
| Carthage | 69 |

None of them had been checked, and none said what it shows about the Bible. They put gold dots
across Egypt and Mesopotamia. They also made the map's finds file 1.25 MB, which every visitor
downloaded.

The import now looks only at places in and near the Holy Land: Israel, the Palestinian
territories, western Jordan, southern Lebanon and Syria (Tyre, Sidon, Byblos, Damascus), and the
northern Sinai. It also skips items that have no English name in Wikidata.

A test run with the new limit found 61 finds instead of 1,192. They include the Mesha Stele,
which names King Omri of Israel, and an ossuary and an epitaph from Jerusalem.

### Why

Wikidata lists thousands of objects from big museum collections, like the Louvre's and the Museo
Egizio's. Most come from places the Bible names, but they say nothing about the Bible itself. The
map is about the world of the Bible, so finds from far away are better added by hand, one at a
time, with a note saying what each one shows.

### How it works

The area is set in one place, `REGION` in `scripts/import_wikidata_artifacts.py`. Widen it there,
and the next weekly run imports the new area.

When the import finishes, it removes any Wikidata find it no longer returns. So the next run
deletes the far-away finds by itself. Hand-picked finds are never removed.

## Unchecked finds stay off the map

### What changed

The map now shows only finds that a person has checked. The finds card under the map has a new
checkbox, "Also show … finds not yet reviewed". Ticking it adds the Wikidata imports, labeled
"Being checked".

### Why

An imported find hasn't been looked at by anyone on this site. It might be dated wrongly or linked
to the wrong place. Visitors should see checked finds first, and see unchecked ones only when they
choose to.

## Daily readings stopped loading

### What happened

From November 23, the Readings page said "The readings for this day haven't been loaded yet."
The Daily jobs workflow still ran every day and showed as passing, but it saved nothing.

USCCB changed how its readings pages are laid out. The `catholic-mass-readings` package (0.8.1,
the newest) looks for the reading text in a place that no longer exists, and then fails on the
whole day. The job caught each failure, wrote it to the log, and finished as if all was well.

### What changed

- The job now reads USCCB's new layout itself. It finds every reading's name and reference on
  the page, and skips the reading text, which the site never stores anyway. Book names and
  labels still come from the package, so new days look the same as older ones ("First Reading",
  "Psalms 96:10, 11-12, 13"). Pages in the old layout still go through the package unchanged.
- Days without a second reading, like most weekdays, work as before. Only the Gospel is
  required.
- A day is saved only if it includes a Gospel. Every Mass has one, so a day without it means the
  page wasn't read properly. Saving it anyway would lock in the gap, because the job never fetches
  a stored date again.
- If any day fails, the workflow now ends with an error and shows red on the Actions tab, with
  a line for each day saying what was missing.

### How it was checked

A test reads a saved copy of the November 24 page, with the reading text removed because it is
copyrighted (`backend/tests/fixtures/usccb_2026-11-24.html`). A live fetch on November 24 found all
four parts of that day: Revelation 14:14-19, Psalms 96:10, 11-12, 13, Revelation 2:10c, and
Luke 21:5-11.

### Catching up the missing days

A check of every day from November 2 to December 1 found three bad ones:

| Day | Problem |
|---|---|
| November 23 | Missing: the job failed that day |
| November 24 | Missing: the fix ran after the day had passed, and the job only looks ahead |
| November 26 (Thanksgiving) | Stored on November 20 with no readings at all, before the Gospel check existed |

Two more changes fix those:

- A stored day without a Gospel now counts as missing, so the next run fetches it again and
  replaces it. That covers Thanksgiving.
- The job can fill in past days: `python -m app.jobs.fetch_daily_readings --from 2026-11-23`.
  The Daily jobs workflow's **Run workflow** button now has a box for this date.

To catch up, run Daily jobs from the Actions tab with `2026-11-23` in that box.

Thanksgiving's page may list two sets of readings (the Thursday weekday Mass and the Thanksgiving
Day Mass). It couldn't be tested from the computer this was built on, because USCCB asked for its
browser check there. If the run still can't read it, the run shows red and names the day.
